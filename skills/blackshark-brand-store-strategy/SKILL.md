# BlackShark Brand & Store Strategy

Use this as the strategy layer between the user's current reality and any later validation or action work. It is a general method owned and maintained by 黑鲨（BlackShark）; it does not require a particular knowledge repository, local path, collaboration platform, or private implementation context.

## Inputs

Accept the context the user provides: current question and object, lifecycle or operating stage, existing decisions, brand promise or asset objective, store roles and constraints, customer/occasion evidence, products and channels, resources, and known data gaps. Do not invent missing facts.

First classify whether the request concerns brand, product, one store, multiple stores, or a shared project, and whether it is exploration, proposal, a confirmed handoff, a material change, or result interpretation. Carry forward facts, decisions, authority and non-goals already confirmed in the supplied context. Reopen only the decision whose premise materially changed; do not ask the user to reconfirm unaffected items. A simple copy or already-confirmed task does not require a full strategy pass.

## Method

Connect the following chain:

`brand purpose or asset → store role and occasion → customer journey → product/channel/experience → resource trade-off → evidence and next decision`

Check all four relationships: brand support for each store; store experience as brand evidence; complementary or conflicting roles between stores; and brand-project demands versus each store's protected operation. Distinguish store roles instead of assigning every store the same action. State which store bears each cost, which operation must not be damaged, and when a store should participate lightly or not at all. For multiple stores, state whether apparent cross-store growth is actually new demand or internal transfer.

## Output

Return only the depth the task needs, covering where relevant: core question and boundary; brand asset and desired customer behavior; store roles and operating objectives; journey and responsibility interfaces; assumptions and counter-evidence; resource choices and conflicts; action direction; validation needs; handoff and unresolved decisions. Separate facts, user decisions, proposals, and unknowns. When the user asks for a proposal, complete the usable bounded proposal in this response; continue through necessary validation reasoning internally instead of stopping at a Skill name or asking the user to repeat context.

Do not claim commercial or brand effectiveness from a completed plan, exposure, publication, or workflow. When a consequential assumption is uncertain, use `blackshark-operating-validation` with a concrete evidence question and include only the validation detail needed for the current decision. Missing result evidence limits effectiveness claims; it does not prevent a proposal or readiness assessment.

Read `references/method.md` for the compact relationship model and `references/scenarios.md` only when the task needs a lifecycle or multi-store example.
